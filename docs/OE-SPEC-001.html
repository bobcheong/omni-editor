@@ 01 @@ Summary and positioning

What Omni Editor is

Omni Editor edits, compares and merges text files, folders, spreadsheets and documents on an Android device, including files held on remote servers and inside archives — with an engine tuned for files large enough to defeat ordinary mobile viewers.

Two products, one document engine. Omni Editor is a capable standalone text editor and a compare/merge tool. They are not separate features bolted together: a compare pane is an editor pane with a diff overlay, sharing the line index, piece table, undo stack, syntax highlighter and save path. Every capability the editor gains is available inside a compare, and any file being edited can be compared against another in one action.

The category baseline — set by desktop diff and merge tools generally — is: 2- and 3-way text compare and merge, folder compare with rule-based synchronisation, comparison of tabular and document formats, work over remote filesystems, and version-control integration, all in one application. Omni Editor delivers that baseline on a device with one hand, a 6-inch screen, a storage model that hides the filesystem, and a battery. It is an independent product (§16) — the baseline is a description of what the category does, not a product to be cloned.

The product is not a port. Three constraints reshape it and are the source of most decisions in this document:

  • The screen is narrow. Side-by-side is a tablet and landscape layout. Unified (single-column) diff is the phone default, and every navigation affordance assumes the reader cannot see both files at once.
  • There is no filesystem. Android grants access to documents and trees the user explicitly picks. Paths are not durable; URIs and permission grants are. Sessions store grants, not paths.
  • Work is interruptible. A compare or a sync can be backgrounded, killed, or resumed hours later. Long operations run as cancellable, resumable jobs with visible progress.

Positioning statement

For developers, sysadmins, QA engineers and reviewers who need to check what changed while away from a workstation, Omni Editor is a compare tool that handles real files — not a snippet-paste diff toy and not a read-only viewer.

@@ 02 @@ Goals and non-goals

Goals

+G-1

Feature parity of intent. Every compare mode UltraCompare offers — text, folder, table, document, binary, archive — has a first-class mobile equivalent, even where the interaction differs.

+G-2

Large file competence. Files that make other Android editors fail should open and diff. This is the reference product's headline claim and the clearest differentiator.

~G-3

Legible diffs on a phone. A person should understand what changed while standing up, in under ten seconds, without pinching.

+G-4

Trustworthy merges. Writing is destructive. Every merge and sync is previewed, undoable within the session, and backed up before the first write.

+G-5

Works offline. Local compare, table compare, document compare and merge require no network and no account.

+G-6

A real editor, not a viewer. Omni Editor opens and edits files on their own, with the same large-file competence as the compare engine (M5). Compare and edit are two views of one document, not two apps welded together.

Non-goals

−NG-1

Not an IDE. The app edits files, not projects. No build integration, language servers, code completion, debugger, terminal or plugin runtime. The line is: anything that helps you read and change this file is in; anything that requires understanding a codebase is out.

−NG-2

No shell integration equivalent. Android has no file-manager context menu API. The share sheet and ACTION_VIEW handling replace it (§9).

−NG-3

No command line. Automation is served by scheduled sync jobs and (later) an intent API, not a CLI.

−NG-4

Not a Git client. Omni Editor reads repositories to diff and resolve conflicts. It does not stage, commit, push, rebase or manage remotes in v1. See Q-3.

These constraints are not implementation trivia; they determine the product surface. Every one of them removes or reshapes something the desktop product does.

@@ 06 @@ Functional requirements

M1 · Sources and file access

+OE-SRC-1

Source picker. Either side of a compare accepts: device storage (SAF), a saved remote connection, a URL, an archive member, a Git object, the clipboard, or a pasted snippet. The picker is one screen with a source-type rail, not a chain of dialogs.

~OE-SRC-2

Persistent access. Sessions store a path, an optional persistable URI grant, a human-readable label, and a content fingerprint (size + modified time + first/last 4 KB hash) so a moved file can be re-matched. The direct flavour resolves by path; the store flavour requires the grant (DIST-2).

+OE-SRC-3

Recents and favourites. Recently used files, folders and connections appear first. Favourites are pinnable and survive reinstall via backup.

+OE-SRC-4

Share-sheet ingestion. The app registers as a share target for text/*, application/*, and multi-select. One file → "compare with…" prompt. Two files → compare opens immediately. Text → snippet compare.

+OE-SRC-5

Encoding handling. Auto-detect UTF-8/16/32, BOM, and common 8-bit codepages; per-side manual override; line-ending detection (CRLF/LF/CR) shown in the header and independently ignorable.

~OE-SRC-6

Unresolvable sources. If a grant is revoked or a remote host is unreachable, the session opens in a degraded state showing the last known result marked stale, with a single "Reconnect" action.

M2 · Compare engine

+OE-ENG-1

Algorithm. Histogram diff (Myers fallback) producing line-level hunks, then a second pass producing intra-line character or word ranges for changed line pairs.

+OE-ENG-2

3-way. Diff3 against a common base for merge conflict detection; when no base exists (two arbitrary files plus a third), the middle pane is the base by convention and this is stated in the UI.

~OE-ENG-3

Logical line matching depth is configurable (default 20 lines scanned to re-anchor a block), matching UltraCompare's tunable behaviour.

~OE-ENG-4

Large-file strategy. Below the threshold (default 32 MB) the engine indexes every line. Above it: rolling-hash block matching to locate changed regions, then full diff within those regions only. The mode in use is disclosed in the session header — never silently degraded.

+OE-ENG-5

Ignore rules are applied as a normalisation layer before hashing, so ignored differences never produce hunks: case, leading/trailing/all whitespace, blank lines, line terminators, lines matching begins-with / contains / ends-with, all text between two markers, and N lines at head or tail.

+OE-ENG-6

Column ranges. A rule set of column spans to compare or ignore, expressed 1-based inclusive, applied per side.

+OE-ENG-7

Cancellation and progress. Every compare is cancellable, reports determinate progress once total size is known, and survives configuration change and process death (results cached to disk by session ID).

M3 · Text compare view

~OE-TXT-1

Two layouts. Unified (default <600dp): one column, interleaved, colour-coded gutter markers. Split (default ≥600dp or landscape): synchronised horizontal panes with relational connector lines between matched blocks, as on desktop. A toggle in the app bar switches manually at any width.

+OE-TXT-2

Difference navigation. Previous/next-difference controls are the primary bottom-bar actions. A difference counter reads 7 / 42. Swipe left/right on the content area jumps difference-to-difference (configurable).

+OE-TXT-3

Minimap rail. Full-height, 6dp wide, right edge, showing difference density. Draggable to seek; tap to jump.

+OE-TXT-4

Filter view. Show all lines / only differences / only matches — matching the desktop filter, as a segmented control.

+OE-TXT-5

Syntax highlighting by detected language, themed, disableable per pane. Highlighting must never delay first paint; it applies progressively.

+OE-TXT-6

Display options: word wrap, line numbers, whitespace glyphs, tab width, font family and size, synchronised scrolling on/off, flip sides.

~OE-TXT-7

Active-line inspector. A collapsible bottom sheet showing the current line from every side stacked vertically with intra-line highlighting — this is how a phone user sees "side by side" for the line that matters.

+OE-TXT-8

Bookmarks on lines, listed in a sheet, persisted with the session.

+OE-TXT-9

Status readout: line/column, hunk count, lines added/removed/changed per side, encoding, line ending, engine mode.

~OE-TXT-10

HTML preview. Render either side in a sandboxed WebView (JavaScript disabled by default) to inspect an HTML file visually, replacing the desktop's embedded browser.

M4 · Merge and edit

+OE-MRG-1

Block and line merge. Tap a hunk marker → arrow actions to copy the block in either direction; long-press for line-level and selection-level merge.

+OE-MRG-2

Word-level replace and insert within a changed line pair.

+OE-MRG-3

Accept all in either direction, with a confirmation stating how many hunks and lines will change.

+OE-MRG-4

Unlimited in-session undo/redo of merges and edits. Merged lines are marked for review until saved.

+OE-MRG-5

Safety. Before the first write to a file in a session, a timestamped backup is written to app storage. A "Restore original" action is available for 30 days (configurable, size-capped).

+OE-MRG-6

Dirty-state handling. Unsaved changes survive process death. Leaving a session with unsaved edits prompts save / discard / keep editing.

~OE-MRG-7

External change detection. On resume, re-fingerprint both sources; if either changed underneath, banner: "The file on the left changed. Reload or keep your version."

M5 · Standalone editor

Beyond the reference product. Omni Editor opens, edits and saves files with no compare involved — the editor and the compare view share one document engine, one syntax highlighter and one undo stack.

+OE-EDT-1

Open, create, save. Any source from M1 — device, remote, archive member, URL, Git object — can be opened for editing. Save, Save as (SAF), and Save a copy. Read-only sources (URL, Git history, archive without write support) open in a clearly labelled read-only state with "Save a copy" offered.

+OE-EDT-2

Tabs. Open documents and open compares share one tab strip. A tab shows a dirty dot when unsaved. Tab state, caret position and scroll offset survive process death.

+OE-EDT-3

Large-file editing. The editor uses the same line index and piece-table model as the compare engine, so a 500 MB log opens without loading into memory. Edits are held as a piece list and materialised only on save.

+OE-EDT-4

Find and replace with case sensitivity, whole word, regular expressions (with capture-group references in the replacement), replace all with a count, and find-in-selection.

+OE-EDT-5

Navigation: go to line, bookmarks, jump to matching bracket, and a symbol outline for supported languages.

~OE-EDT-6

Touch editing affordances. A programmer's key row above the keyboard (tab, brackets, quotes, pipe, arrows, undo/redo), draggable caret handle, and long-press-drag for precise selection. Typing on a phone is the weakest part of any mobile editor; this row is where the effort goes.

+OE-EDT-7

Text operations: sort lines, remove duplicate lines, trim trailing whitespace, change case, convert tabs/spaces, convert line endings, convert encoding, join/split lines, insert timestamp. Each is undoable as one step.

+OE-EDT-8

Column (block) selection and multi-caret editing on large screens and with a hardware keyboard; on phones, column select is entered from the selection menu.

+OE-EDT-9

Autosave and recovery. Edits are journalled continuously to app storage. A crash or kill restores every open document byte-exact, unsaved changes included, without prompting.

+OE-EDT-10

Editor ⇄ compare handoff. From an open document: "Compare with…" opens a compare with this document as the left side, including its unsaved buffer. From a compare: "Open in editor" promotes either side to a full editing tab, preserving merge state.

~OE-EDT-11

Remote editing follows a download–edit–upload cycle with an explicit save-to-server step, conflict detection on upload (re-fingerprint before write), and retry on failure without losing the buffer.

−OE-EDT-12

Not in the editor: project/workspace management, build or run integration, language servers, code completion, macros and scripting. Revisit after launch based on demand.

M6 · Folder compare and sync

+OE-FLD-1

2- and 3-folder compare, recursive, over any combination of local, SMB and FTP/SFTP sources.

~OE-FLD-2

Tree presentation. A single merged tree — each row is a relative path with per-side status chips — replaces the desktop's two side-by-side trees, which do not fit a phone. Split trees appear at ≥720dp.

+OE-FLD-3

Comparison method switchable on the fly: basic (name + size + timestamp), full (byte/CRC), smart (content diff for text types).

+OE-FLD-4

CRC-based remote compare to avoid downloading files where the server supports a checksum command; otherwise size+date with an explicit "not content-verified" indicator.

+OE-FLD-5

Filters: include/exclude by glob, NOT operator, ignore listed directories and file types, ignore hidden/system files, ignore timestamp differences, size and date bounds.

+OE-FLD-6

Drill-down. Tapping a differing file opens a text/table/binary compare in a new session, inheriting the folder session's rules.

+OE-FLD-7

Sync rules. Built-in rule sets (mirror left→right, mirror right→left, newest wins, two-way merge) plus user-defined rules with per-condition actions (copy, delete, skip, ask).

+OE-FLD-8

Sync review is mandatory. A pre-flight list shows every planned action with counts and total bytes, per-file override, and a red summary of deletions. Nothing executes before explicit confirmation.

~OE-FLD-9

Scheduled sync via WorkManager, with constraints (unmetered network, charging, idle). Android does not guarantee exact timing; the UI states "runs approximately every…" rather than promising a clock time.

+OE-FLD-10

Find duplicates across two or more folders by any combination of name, size, date and content hash, with keep/delete selection and a bulk action guarded by the same review step as sync.

Sync engine semantics

Sync is the only part of the app that destroys data, so its behaviour is specified rather than left to implementation.

Rule evaluation

for each path in union(left, right):
    state ← classify(path)      // LEFT_ONLY, RIGHT_ONLY, LEFT_NEWER,
                                // RIGHT_NEWER, SIZE_DIFF, CONTENT_DIFF,
                                // IDENTICAL, BOTH_CHANGED, TYPE_CONFLICT
    rule  ← first rule in priority order whose conditions match state
    action ← rule.action ?? ASK
    if action == ASK: add to "Needs your decision"
  • Rules are ordered; the first match wins. The review screen shows which rule produced each action, so an unexpected plan is diagnosable.
  • BOTH_CHANGED — both sides differ from the last recorded sync state — is never auto-resolved by "newest wins". It always requires a decision. This requires storing a sync baseline per session (path → size, mtime, hash) from the previous run.
  • TYPE_CONFLICT (file on one side, directory on the other) is always held for decision.

Write semantics

ConcernBehaviour
AtomicityWrite to a temporary name in the destination directory, then rename. A killed sync never leaves a half-written file at the target path.
ResumeThe plan is persisted before execution and each action is marked done as it completes. An interrupted sync resumes from the first incomplete action; partial transfers restart from zero unless the protocol supports ranged resume (SFTP, HTTP), in which case they resume by offset.
DeletionDefault is move-to-trash inside a hidden .omni-trash folder at the sync root, retained for a configurable period. Permanent delete is opt-in per rule set and confirmed separately.
TimestampsModified time is preserved on copy where the destination supports it. Where it cannot be set (some SAF providers, some FTP servers), the session records this and falls back to content hashing for subsequent runs rather than reporting spurious differences.
Clock skewA configurable tolerance (default 2 s, plus automatic 1-hour allowance for FAT/DST artefacts) prevents a whole tree being reported as changed.
Case sensitivitySyncing a case-sensitive source to a case-insensitive destination detects collisions before execution and reports them as conflicts rather than silently overwriting.
Illegal namesCharacters legal on the source but not the destination are detected at planning time; the user chooses to skip or sanitise.
SymlinksNot followed by default; listed and skipped with a note. Following is an explicit option with cycle detection.
PermissionsPOSIX modes preserved for SFTP↔SFTP. Otherwise not transferable; stated in the report rather than silently dropped.
ConcurrencyTransfers run with bounded parallelism (default 4, 1 on metered networks). Deletions execute after all copies succeed, so a failed copy never leaves a gap.
VerificationOptional post-copy hash verification, on by default for remote destinations.
Free spaceChecked before execution; the plan is blocked with a shortfall figure rather than failing midway.

Scheduled sync

  • Runs as a periodic WorkManager job with constraints; minimum practical interval is 15 minutes and the UI never promises exact times.
  • A scheduled run that produces any ASK action does not execute. It notifies "Sync needs your decision" and holds the plan for review.
  • Fully-automatic mode (no ASK actions possible) is opt-in per session and requires the rule set to be total — every state mapped to a concrete action.
  • Failures retry with exponential backoff; three consecutive failures notify once and pause the schedule.

Connection behaviour

  • Pooling. One authenticated session per connection, reused across compares; idle connections closed after 60 s. FTP data connections are opened per transfer.
  • Retry. Transient failures (timeout, reset, 4xx FTP reply) retry three times with backoff. Authentication and host-key failures never retry — they surface immediately.
  • Interruption. Losing Wi-Fi mid-listing marks the tree partial and offers resume rather than discarding the scan.
  • Character sets. Per-connection filename encoding (UTF-8 default, with legacy codepage options) because FTP servers routinely disagree.
  • Path handling. Remote roots are stored as protocol + host + absolute path; the app never assumes a home directory.
  • Metered networks. Transfers above the threshold prompt once per session; scheduled syncs default to unmetered-only.
  • Certificates. System trust store plus user-imported CAs; self-signed acceptance is per-connection, recorded with its fingerprint, and never global.

Module contracts

These interfaces are the seams the modules are built against. They exist so the diff core, the editor and the transfer layer can be developed and tested independently of Android.

// :core:io — one abstraction over every source kind.
interface SourceProvider {
    suspend fun resolve(ref: SourceRef): Resolved      // label, size, mtime, mime, capabilities
    suspend fun open(ref: SourceRef): ByteChannel      // random access where supported
    suspend fun write(ref: SourceRef, from: ByteChannel, atomic: Boolean = true)
    suspend fun list(ref: SourceRef, recursive: Boolean): Flow<Entry>
    fun capabilities(ref: SourceRef): Capabilities     // checksum, setMtime, resume, write
}

// :core:io — the shared document model. The editor and both compare panes use this.
interface TextDocument {
    val lineCount: Long
    fun line(index: Long): CharSequence                // O(1) via the line index
    fun edit(range: LongRange, replacement: CharSequence): EditId
    fun undo(): EditId?; fun redo(): EditId?
    suspend fun materialise(into: ByteChannel)         // piece table → bytes, on save only
    val changes: Flow<DocumentChange>                  // drives re-diff and re-highlight
}

// :core:diff — pure, cancellable, no Android types.
interface DiffEngine {
    suspend fun compare(
        left: TextDocument, right: TextDocument, base: TextDocument? = null,
        rules: RuleSet, progress: (Progress) -> Unit
    ): CompareResult
    fun intraLine(pair: LinePair, granularity: Granularity): List<Range>   // lazy, per visible row
}

// :feature:folder — planning is separate from execution, and always inspectable.
interface SyncPlanner {
    suspend fun plan(result: FolderCompareResult, rules: List<SyncRule>,
                     baseline: SyncBaseline?): SyncPlan
}
interface SyncExecutor {
    suspend fun execute(plan: SyncPlan, progress: (SyncProgress) -> Unit): SyncReport
    suspend fun resume(planId: String, progress: (SyncProgress) -> Unit): SyncReport
}

Why plan and execute are separate types. The review screen (S-06) renders a SyncPlan and nothing else. Because execution consumes the same object the user approved, the preview cannot drift from the action — which is the single most important correctness property in the app, and it is enforced by the type system rather than by discipline.

Threading and cancellation

  • Two bounded dispatchers: ioPool (size 8, network and storage) and computePool (size = cores − 1, diffing and hashing). The main thread does layout only.
  • Every long operation is a coroutine scoped to its session, cancelled when the session closes and re-attachable after configuration change. Diff loops check ensureActive() every 4 096 lines.
  • Results stream: hunks are emitted as found, so the first difference renders before the compare finishes.
  • Back-pressure via Flow buffering with conflation on progress updates — progress never becomes the bottleneck.

@@ 14 @@ Test strategy

How correctness is demonstrated

  • Golden-file corpus. A fixed set of file pairs — source code, minified JS, CSV with reordered rows, CRLF vs LF, UTF-16 with BOM, files with no trailing newline, 1-byte files, empty files, 2 GB log files — each with an expected hunk set checked into the repository. Any engine change diffed against these.
  • Differential testing against GNU diff and git diff output for the same inputs, tolerating known algorithmic differences but flagging semantic ones.
  • Property tests: applying all left-to-right merges must make the files identical; undo must restore byte-exact originals; ignore rules must never increase the hunk count.
  • Sync dry-run tests asserting that the preview list exactly matches what execution performs, on a simulated filesystem including failure injection mid-sync.
  • Device matrix: low-RAM phone (4 GB, Android 10), mainstream phone (current), foldable, 11" tablet, DeX. Macrobenchmark for NFR-P1..P6 in CI.
  • Accessibility: automated Compose a11y checks plus a manual TalkBack pass on the text, folder and sync-review flows each release.
  • Security: credential storage audit, TLS/host-key negative tests, and a check that no path, hostname or file content appears in logs or crash payloads.

@@ 16 @@ Independence, distribution and build

Independence

Omni Editor is an independent product with no relationship to any existing compare or editor tool, its publisher, or its brand. This is a build constraint, not a legal footnote — it binds naming, assets, formats and copy.

+IND-1

No naming association. The product name, package ID, app label, icon, splash, store copy and documentation make no reference to any other product or vendor. Package ID is a new namespace with no third-party token in it. No "compatible with", "alternative to" or "works like" claims anywhere in the app or its materials.

+IND-2

No third-party assets. No icons, colour schemes, theme files, screenshots, help text, marketing copy or documentation from another product. All UI copy is written for this product; all icons are original or from a permissively licensed set with attribution recorded.

+IND-3

No third-party file formats. Themes, syntax grammars, ignore rules, sync rules and session definitions all use formats designed for this app. The app does not read, write, import or claim compatibility with any other tool's configuration format. This is the reason OE-TXT-5 dropped its grammar-import path.

+IND-4

Independent interface design. The UI is derived from Material 3 and the mobile constraints in §4, not from another product's layout. Diff colour conventions (green added, red removed) and standard terminology (hunk, 3-way merge, unified diff) are industry-wide conventions and remain fine to use.

+IND-5

Dependency licence hygiene. Every third-party library is checked before adoption: Apache-2.0, MIT, BSD acceptable; LGPL only if dynamically linked and documented; GPL and AGPL excluded. A generated licenses.md and an in-app licences screen are part of the definition of done. Two specific checks: the RAR decoder (Q-6) and any document-parsing library, which is where restrictive licences cluster.

+IND-6

No AI-generated code that reproduces a specific implementation. Claude Code implements from this specification and from public algorithm literature (Myers, histogram diff, piece tables). If any generated code appears to reproduce an identifiable third-party implementation, it is rewritten.

Distribution

Release one is installed directly as an APK, not published to a store. That changes three decisions that were previously made under Play policy constraints.

~DIST-1

Two build flavours from one codebase. direct and store. They differ only in a manifest, a permission, and one implementation of SourceProvider. Keeping both from day one costs little; retrofitting the store flavour later would mean reworking every file-access path.

~DIST-2

Storage model reverses for the direct flavour. With MANAGE_EXTERNAL_STORAGE, the app gets real paths and a real file browser — no per-file SAF picker, durable path-based sessions, and far better folder-compare ergonomics. The store flavour keeps SAF. SourceProvider (§10) already abstracts this; the two flavours supply different implementations and the rest of the app is unaware.

Consequence: sessions store a path plus an optional URI grant. The direct flavour prefers the path; the store flavour requires the grant. Session export between flavours degrades gracefully rather than failing.

~DIST-3

No billing, no accounts, no entitlement in P1. Module M18 becomes a no-op: everything is unlocked. The tier split in OE-LIC-2 is retained in this document only as a record of what a future paid split could be. No account SDK, no licence check, no phone-home.

+DIST-4

Signing and updates. A release keystore is generated once and kept out of the repository; the same key must be used for every build so sideloaded updates install over the previous version. Version code is monotonic; version name is major.minor.patch. An in-app "check for update" is out of scope — updates are delivered as APKs.

+DIST-5

Store-readiness is maintained, not deferred. The store flavour must build and pass tests in CI from the first sprint, even though it is not shipped. Data-safety-relevant behaviour (no telemetry by default, no secrets in backups) holds in both flavours.

Build conventions for Claude Code

The implementation is generated by Claude Code, which changes how this specification should be consumed: requirement IDs become the unit of work, and acceptance criteria matter more than prose.

  • A CLAUDE.md at the repository root carries the non-negotiables: module boundaries, the independence rules above, the licence policy, the "no generic error path" rule, and the instruction that :core:* modules must not import Android types.
  • Work is tracked by requirement ID. A commit message references the IDs it satisfies; a requirement is done when its acceptance criteria pass in CI.
  • Every module lands with tests in the same change. The golden-file corpus (§14) is created before the diff engine, not after.
  • Architecture decisions that deviate from §10 are recorded as short ADRs in docs/adr/ rather than silently absorbed.
  • The detailed P1 task sequence, repo scaffold and per-task acceptance criteria live in the companion build plan document.
